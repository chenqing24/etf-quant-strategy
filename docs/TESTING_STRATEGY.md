## 一、用户接触面回归测试

### 1.1 教训（US-008 + 2026-06-03）

**核心教训**：测试覆盖率 100% ≠ 业务正确

US-008 改了 `can_buy()` 默认值（1→2），但报告顶部仍写"单持仓"——因为没测报告输出。
US-008 自评 96 分"优秀"，实际上业务输出脱钩——**扣分到 88-90 才合理**。

### 1.2 规则

任何"用户能看到的输出"必须有测试覆盖：
- [ ] CLI 输出（决策报告、持仓指导、错误信息）
- [ ] 日志（ERROR/WARN 必须有对应测试）
- [ ] 报告（每段硬编码文案必须有"动态生成"测试）
- [ ] 钉钉推送（有动作/警告必须能验证触发）

### 1.3 检查清单（每次 PR）

```
[ ] 改了业务规则？ → 报告输出段有测试？
[ ] 改了默认值？  → 报告顶部"策略模式"段有测试？
[ ] 改了数据源？  → 报告"资金配置"段有测试？
[ ] 改了状态机？  → 报告"动作清单"段有测试？
[ ] 加了新模式？  → CLI -m 模式有 E2E 测试？
[ ] 改了文案？    → 关键文本（操作建议/情景分析）有测试？
```

## 二、测试分层（D7=A：复用 US-009 fixture）

### 2.1 Fixture 标准

| 类型 | 路径 | 用途 |
|------|------|------|
| **隔离 DB** | `tmpdir/test.db` + schema/004 | 业务逻辑测试（US-008/009/010/013）|
| **隔离 realtime_cache** | `tmpdir/test.db` + CREATE TABLE | PositionGuide 测试 |
| **隔离 performance.json** | `tmpdir/etf_performance.json` | TradeTracker 测试 |

### 2.2 不允许（教训 71）

- ❌ 用真实 DB 测试（污染生产数据）
- ❌ 用 mock-based 测核心路径（少覆盖）
- ✅ 用临时 db_path 隔离

## 三、回归测试策略（D8=B：每次新 US 跑全量回归）

### 3.1 测试范围

| 测试 | 类型 | 范围 |
|------|------|------|
| 单元测试 | `tests/unit/` | 单个函数/类 |
| E2E 测试 | `tests/e2e/` | CLI 子命令端到端 |
| 集成测试 | `tests/integration/` | 跨模块 |

### 3.2 回归频率

| 阶段 | 跑哪些 |
|------|--------|
| 本地开发 | 只跑新 US 的测试 |
| PR 提交 | 跑全量（unit + e2e + integration）|
| CI | 跑全量 + 多个 Python 版本 |

### 3.3 pre-existing 失败

历史遗留的 6-8 个失败不算阻塞（如 `test_cli_paths::test_no_old_style_imports`、`test_etf_name_from_db::test_update_names` 等）。
**新增失败才算回归**。
